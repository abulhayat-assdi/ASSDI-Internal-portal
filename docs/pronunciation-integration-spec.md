# Bangla Pronunciation app → ASM Portal: integration spec

For: the maintainer of `lavlu1211/accent`
Status: agreed requirements, 2026-11-22. Nothing on the portal side is built yet.

## What changes, in one paragraph

The app moves from Namecheap/cPanel to the portal's VPS (Coolify). It runs as its own container, built
from your repo, and redeploys automatically whenever you push to `main`. It is served at
`https://<course domain>/pronunciation/`, on the same domain as the portal. Trainees and staff no longer
log in to the app directly: they open it from the portal, which signs them in. Data moves from MySQL to
the portal's PostgreSQL server. The app gets its own database there, so its tables stay separate from
the portal's own tables. All current trainees, progress and recordings move across.

You keep full ownership of the app's code. The portal side (menu item, per-course on/off switch, sign-in
hand-off, server setup) is done in the portal repo.

---

## 1. Container build (`Dockerfile` at repo root)

- Multi-stage build: build `frontend` (`npm ci && npm run build:deploy`, which needs `backend/scoring`),
  then a slim Node 20 runtime with `backend` (`npm ci --omit=dev`), `ffmpeg` installed from apt, and
  `CMD ["node", "server.js"]`.
- Listen on `PORT` (default `5000`).
- Recordings are written to `/app/backend/uploads`. That path becomes a persistent volume, so nothing
  else may be written there at build time.
- `GET /pronunciation/api/health` must return 200 only when the database is reachable. Coolify uses it
  as the health check.
- Database migrations run on start, before `listen()` (see §3). A failed migration must exit the process
  with a non-zero code, so a broken deploy never goes live.

## 2. Serving under `/pronunciation`

Everything must work under a path prefix. Make it configurable with `BASE_PATH=/pronunciation`, and
`''` for local development.

- Vite: `base: '/pronunciation/'` (from an env var at build time).
- `frontend/src/config.js`: `API = BASE_PATH + '/api'`, and `mediaSrc` also prefixes `BASE_PATH`.
- React Router: `basename={BASE_PATH}`. This covers `/admin` and every hard-coded link or
  `window.location` redirect.
- Express: mount the whole app on a router at `BASE_PATH` (API, `/api/media/*`, static files, and the
  SPA fallback). Signed media links must include the prefix.
- Do not rely on the proxy stripping the prefix. The app receives the full `/pronunciation/...` path.
- `X-Frame-Options: SAMEORIGIN` and `Permissions-Policy: microphone=(self)` can stay as they are, because
  the app is on the same origin as the portal.
- `trust proxy` stays on (Traefik is in front).

## 3. PostgreSQL instead of MySQL

- Replace `mysql2` with `pg` (node-postgres). Connect with `DATABASE_URL`
  (`postgres://pronunciation_app:...@<host>:5432/pronunciation`).
- The app gets its own database, `pronunciation`, and a role that owns only that database. It has no
  access to the portal's tables.
- Port `schema.sql` and migrations `001`–`007` into one Postgres baseline (`migrations/pg/0001_baseline.sql`).
  After that, add new numbered files only. Track applied files in a `schema_migrations` table and run
  pending ones automatically on start (the `db:migrate` logic, run at boot).
- Things to watch when porting:
  - `?` placeholders become `$1, $2, …`.
  - `AUTO_INCREMENT` becomes `GENERATED BY DEFAULT AS IDENTITY`.
  - `INSERT ... ON DUPLICATE KEY UPDATE` becomes `INSERT ... ON CONFLICT (...) DO UPDATE`.
  - `insertId` becomes `RETURNING id`.
  - Backticks become double quotes, or remove them.
  - `TINYINT(1)` becomes `boolean`. The code currently does `Number(x)` on these, so check every use.
  - `DATETIME` becomes `timestamptz`. Keep `APP_TIMEZONE=Asia/Dhaka` for calendar-day logic.
  - `GROUP_CONCAT` becomes `string_agg`. `IFNULL` becomes `COALESCE`. `LIMIT a, b` becomes
    `LIMIT b OFFSET a`.
  - Case sensitivity: MySQL's default collation compares strings case-insensitively. Postgres does not.
  - Postgres stores UTF-8 natively, so the `utf8mb4`/garbled-Bangla handling is no longer needed.
- The existing end-to-end tests in `backend/tests` should pass against a Postgres test database.
  That is the acceptance check for this part.

## 4. Sign-in from the portal (SSO)

The portal decides who may use the app (logged in, the course has the feature on, and the right role
for staff). The app trusts the portal's signed hand-off.

### Hand-off

The portal redirects the browser to:

```
GET /pronunciation/sso?token=<JWT>
```

`<JWT>` is HS256-signed with the shared secret `PORTAL_SSO_SECRET` (env var, at least 32 bytes, the
same value on both sides). Claims:

| claim | meaning |
|---|---|
| `iss` | `"asm-portal"` |
| `aud` | `"pronunciation"` |
| `sub` | portal user id (opaque text id, `[A-Za-z0-9_-]{1,64}`) |
| `course_id` | portal course id (opaque text id — cuid or UUID, `[A-Za-z0-9_-]{1,64}`). The same person in two courses means two separate accounts, as in the portal. |
| `role` | `"trainee"`, `"trainer"` or `"admin"` |
| `name` | display name |
| `email` | portal login email |
| `mobile` | mobile number if the portal has it, else omitted |
| `batch`, `roll` | trainee only, may be omitted |
| `iat`, `exp` | `exp` is at most 60 seconds after `iat` |
| `jti` | random id |

### What `/sso` must do

1. Verify the signature, `iss`, `aud`, `exp` (allow 30 s clock skew), and that `jti` has not been used
   before. Store used `jti` values until they expire, so each link works once.
2. Find the account by (`portal_user_id`, `course_id`). If there is none, use the one-time legacy link
   in §5. If that also finds nothing, create the account. Update the name, role and mobile from the
   token on every sign-in.
3. Issue the app's own session (the existing trainee token or admin token, by role) and redirect to the
   trainee dashboard or to `/pronunciation/admin`. Do not leave the JWT in the address bar.
4. On any failure, show a plain page saying "পোর্টাল থেকে আবার খুলুন" (open it again from the portal),
   with a link back to the portal.

### Role mapping

- `trainee`: the trainee app.
- `trainer`: the current Trainer role (record audio, content, grading).
- `admin`: the current Admin role.

The portal sends `trainer`/`admin` only to staff it has given the Pronunciation permissions.

### Turn off direct access

- Remove or disable trainee register, login, forgot-password and change-password, plus the
  trainer/admin login form. Keep the endpoints returning 410, with a link to the portal.
- Keep exactly one break-glass login: the env Super Admin (`ADMIN_MOBILE` + `ADMIN_PASSWORD`), at
  `/pronunciation/admin/login`, for emergencies only.
- Deactivating or removing a user in the portal must stop access the next time the app checks.
  Simplest approach: make app sessions short (for example 12 h) so they need a fresh hand-off. The
  30-day trainee token is no longer needed, because the portal session covers "stay logged in".

### Schema additions

- On `users` and on the staff/trainer table: `portal_user_id text`, `course_id text`, and
  `UNIQUE (portal_user_id, course_id)`.
- `sso_used_jti (jti text primary key, expires_at timestamptz)`.

## 5. Moving the live data from Namecheap

The goal: one cut-over with no lost trainees, progress or recordings.

1. Write `npm run db:import-mysql -- <dump.sql> <uploads-dir>`. It reads a MySQL dump of the current
   database and loads it into the new Postgres database. Keep all ids, so recording paths and progress
   rows stay valid. Reset identity sequences afterwards. Print row counts per table, old against new.
2. Imported accounts have no `portal_user_id` yet. On their first portal sign-in they are linked
   **once**:
   - Trainees: by mobile number (normalise `+880`/`880`/`0` and spaces), within the same course.
   - Staff: by mobile number.
   - If there is no match, a new empty account is created. Unmatched legacy accounts get an admin
     screen that lists them, so an admin can link them by hand ("link to portal user").
3. Dry run first: copy the data across while Namecheap keeps running, check the counts and spot-check a
   few trainees.
4. Cut-over day:
   1. Put Namecheap in read-only or maintenance mode.
   2. Take the final dump and the `uploads` zip.
   3. Run the import on the VPS.
   4. Replace the Namecheap site with a redirect to the portal.

What we need from you for the migration: the MySQL export (cPanel → phpMyAdmin → Export, SQL format)
and a zip of `backend/uploads`. Send them privately, not through GitHub: they contain trainees' voice
recordings and phone numbers.

## 7. Auto-deploy (one-time setup, about 5 minutes)

We will send you a webhook URL and secret from Coolify. Add them in **Settings → Webhooks** of
`lavlu1211/accent`, with content type `application/json` and only the `push` event. After that, each
push to `main` builds and deploys. A build that fails, or a migration that fails, keeps the previous
version live.

Because the repo is public, keep secrets, database dumps and recordings out of it. `.env` and
`backend/uploads` must stay git-ignored.

## 8. Order of work and hand-off checks

| # | Who | What | Done when |
|---|---|---|---|
| 1 | accent | Postgres port (§3) | e2e tests pass on Postgres |
| 2 | accent | Base path (§2) + Dockerfile (§1) | `docker run` serves `/pronunciation/` locally |
| 3 | accent | `/sso` + direct-login removal (§4) | a test JWT signed with a local secret signs in as a trainee, a trainer and an admin |
| 4 | portal | Feature switch, menu item, launch endpoint, staff permissions | — |
| 5 | portal | Coolify app, database + role, `/pronunciation` route, uploads volume, webhook | health check green on the VPS |
| 6 | accent | `db:import-mysql` (§5) | dry-run counts match |
| 7 | both | Test with one course, then cut over | — |

Steps 1–3 and 4–5 can go in parallel. The only shared contract is §4 (token format and secret).
